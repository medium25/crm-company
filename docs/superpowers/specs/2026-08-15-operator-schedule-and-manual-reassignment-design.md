# Расписание операторов и ручной перевод лидов

## Проблема

Распределение новых лидов (`assignLeastLoadedOperator` / `nextLeastLoadedOperator_`)
смотрит только на текущую загрузку активных операторов — не на то, работает
ли оператор прямо сейчас. Лид, пришедший в 9:05, может достаться оператору,
у которого смена с 14:00, просто потому что у него меньше карточек, вместо
того, кто реально на месте. Расписания операторов в системе вообще нет.

Второй пробел — `assignedOperator` пишется один раз при создании лида и
дальше никогда не меняется руками. Нет способа перекинуть карточки от
одного оператора к другому (увольнение, отпуск, перекос нагрузки) — ни по
одной, ни массово.

## Что меняется

### Расписание оператора

Хранится в `settings/{branchId}.operatorSchedules` — объект вида
`{ [staffId]: WeekSchedule }`, а не на самом `staff/{id}`: правило
Firestore для `staff.update` разрешает менять не-`teacher` записи (то есть
ceo/manager/admin — как раз пул операторов) только вызывающему с ролью
ceo/manager, `admin` получит `permission-denied`. `settings/{id}` пишется
любой admin-ролью без этого ограничения — тот же документ, что уже хранит
`activeLeadOperators`.

`WeekSchedule` — массив длины 7, индекс = `date.getDay()` (0=Вс…6=Сб, та же
конвенция, что в `lib/schedule.js`). Каждый элемент — `null` (выходной) или
`{ start: "09:00", end: "18:00" }`.

Нет записи для оператора в `operatorSchedules` — тех.дефолт «работает
всегда» (та же защита, что у `activeLeadOperators === null` сейчас: чтобы
не настроенное расписание молча не убрало оператора из распределения). По
факту расписание планируется выставить руками всем операторам сразу после
раскатки.

UI — в `LeadAssignmentTab`, у строки оператора кнопка «Расписание» →
модалка `OperatorScheduleModal` с 7 строками (Пн…Вс), чекбокс «рабочий
день» + два time-инпута (начало/конец), кнопка «Сохранить» пишет весь
`operatorSchedules` объект в `settings/{branchId}` (merge).

### Приоритет расписания при назначении

Новая функция в `lib/leadFunnel.js`:

```
isOperatorWorkingAt(schedule, date) // schedule — WeekSchedule | undefined
```
`undefined`/нет записи на этот день → `true` (тех.дефолт «всегда работает»
для дня без записи ведёт себя так же, как отсутствие расписания целиком).
Иначе — день недели совпадает и `start <= "HH:MM" < end` (строковое
сравнение "09:00" работает как числовое благодаря фиксированному формату).

`assignLeastLoadedOperator` меняет сигнатуру — вместо списка id теперь
принимает список операторов с их `workSchedule` и момент времени лида:

1. Из активных операторов отбирает тех, для кого `isOperatorWorkingAt(...,
   createdAt)` — `true`.
2. Если список непустой — наименее загруженный (new+calling) среди НИХ.
3. Если пустой (никто не работает в этот момент) — прежнее поведение:
   наименее загруженный среди ВСЕХ активных.

Время сравнивается как есть (часы окружения выполнения), без привязки к
`branch.timezone` — так же, как уже работает `isWithinWorkingHours` в этом
же файле; не вводим новой сложности сверх существующего допущения.

Меняются оба места создания лида, чтобы поведение не расходилось:

- `StudentFormModal.jsx` — сейчас берёт только id через
  `getActiveLeadOperators`; нужно дополнительно подтянуть `operatorSchedules`
  из `settings/{branchId}` (уже читается через `useDoc` в
  `LeadAssignmentTab`, здесь — разовый `getDoc`) и передать в
  `assignLeastLoadedOperator` вместе с `new Date()`.
- `Code.gs` / `nextLeastLoadedOperator_` — та же логика на своём рантайме:
  дочитать `operatorSchedules` из уже загруженного `settings` дока,
  отфильтровать `ids` по рабочему времени на момент `effectiveCreatedAt`
  (важно — не `new Date()`, лид может быть исторический из Google Sheets),
  fallback на весь список, если фильтр пустой.

### Ручной перевод лидов

В `LeadAssignmentTab`, у строки оператора — разворот (стрелка/клик по
строке) со списком его активных лидов (`funnelStage` не в `['won',
'lost']`), сгруппированных по стадии: Новый лид / Дозвон / Пробный назначен
/ Дожим. У каждой группы — чекбокс «выбрать всю группу» + чекбоксы на
отдельные карточки (имя + телефон). Под списком — `Select` с выбором
оператора-получателя (остальные активные операторы) и кнопка «Перевести
выбранных» (disabled, пока не отмечена ни одна карточка).

Отдельная кнопка «Перевести всех» на самой строке (без разворота) — тот же
выбор получателя, переносит все активные лиды оператора одним действием.

Перевод — `writeBatch`: на каждый лид `assignedOperator: newId, updatedAt:
serverTimestamp(), updatedBy: user.uid`. `funnelStage`, `stageHistory`,
дедлайн-поля (`nextCallDueAt`, `trialConfirmDueAt`, `nextTouchAt`) не
трогаются — переезжает только владелец, прогресс по воронке остаётся как
есть. Батч режется чанками по 400 (лимит Firestore — 500 операций) на
случай, если у оператора скопилось много карточек.

## Данные

- `settings/{branchId}.operatorSchedules: { [staffId]: Array<{start:string,
  end:string}|null> }` (длина массива 7, индекс = день недели, 0=Вс).
  Отсутствие ключа/дня = работает всегда.
- Новых полей на `students` нет — перевод лида это существующее поле
  `assignedOperator`.
- Правила Firestore не меняются — `settings` и `students` уже пишутся через
  `isAdmin()` без дополнительных условий.

## Не входит в эту итерацию

- Учёт `branch.timezone` при сравнении рабочих часов — сравниваем как есть,
  в духе уже работающего `isWithinWorkingHours`.
- Автоматическая перебалансировка карточек оператора, у которого расписание
  закончилось посреди дня (смена в 14:00 не переносит уже назначенные лиды)
  — перевод только вручную через этот же экран.
- Отдельный лог истории переводов сверх `updatedBy`/`updatedAt` на самом
  лиде.
- Пересчёт приоритетной метки (`isPriorityLead`) или SLA-дедлайна при
  ручном переводе — это метки момента создания лида, не владельца.
