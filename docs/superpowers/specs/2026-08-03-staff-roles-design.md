# Роли сотрудников и вход в систему

## Проблема

Сейчас 4 роли (`owner`/`admin`/`accountant`/`teacher`), но нет способа завести
нового сотрудника в приложении — `StaffSettingsTab` только меняет роль тем,
у кого уже есть `staff/{uid}` документ (аккаунт создаётся вручную скриптом,
как `scripts/seed.js`). Роль `accountant` не нужна — заказчик хочет 3
равнозначные "полного доступа" должности + учитель.

## Роли

| Было | Стало | Права |
|---|---|---|
| `owner` | `ceo` | Полный доступ |
| `admin` | `manager` (новая) | Полный доступ |
| — | `admin` (переиспользуем строку) | Полный доступ — это "Администратор" |
| `accountant` | удалена | — |
| `teacher` | `teacher` | Только свои группы + посещаемость |

`ceo`/`manager`/`admin` — везде одинаковые права, никакой иерархии между
собой. Единственная асимметрия сохраняется по смыслу (не по коду): всё, что
раньше требовало `isOwner()` (управление сотрудниками, филиалами, настройками)
— становится доступно всем трём, а не только `owner`.

## Что меняется

### `src/hooks/useRole.js`
`isAdmin` = `role in ['ceo','manager','admin']` (было `owner`/`admin`).
`isFinance` — удаляется (заменяется на `isAdmin`, т.к. `accountant` пропадает).
`isOwner` — удаляется как отдельное понятие в UI-хуке (заменяется `isAdmin`).

### `firestore.rules`
- `isAdmin()` = `role() in ['ceo','manager','admin']`.
- `isFinance()` — убрать, заменить все использования на `isAdmin()`.
- `isOwner()`-гейты (`staff` write, `branches` write, `settings` write) —
  заменить на `isAdmin()` (все три роли, не только ceo).
- `students/{id}` read: убрать `isTeacher()` из списка разрешённых — учитель
  не должен читать всю коллекцию студентов (баланс, телефон и т.д.), только
  то, что нужно для ростера своей группы через `enrollments` (уже разрешено
  отдельным правилом).

### `src/components/layout/Sidebar.jsx`
`ROLE_ITEM_KEYS`: `ceo`/`manager`/`admin` — весь список пунктов (как было у
`owner`). `teacher` — без изменений (`dashboard`, `groups`).

### `src/components/settings/StaffSettingsTab.jsx`
Новая кнопка "Добавить сотрудника" → модалка (имя, email, пароль, должность,
для учителя — привязка к `teachers/{id}`). По сабмиту:
1. Создать Firebase Auth пользователя через **отдельный, временный instance**
   Firebase App (`initializeApp(config, 'staff-create-' + Date.now())`) —
   стандартный обход того, что `createUserWithEmailAndPassword` иначе
   переключает текущую сессию на новый аккаунт. Временный instance сразу
   после создания аккаунта удаляется (`deleteApp`).
2. Записать `staff/{uid}` с выбранной ролью, `isActive: true`.
`ROLE_OPTIONS` — CEO / Менеджер / Администратор / Учитель, без "Бухгалтер".

### Миграция данных
Скрипт `scripts/_migrate_staff_roles.mjs`: единственная существующая запись
`staff` (role: `owner`) → `role: 'ceo'`. Разово, руками подтверждается перед
записью в боевую базу (как и все прошлые записи в этой сессии).

## Не входит в эту итерацию

- Различия в правах между `ceo`/`manager`/`admin` (сейчас идентичны)
- Восстановление роли "бухгалтер" или другая финансовая роль
- Смена пароля/деактивация через email-приглашение (пароль вводит тот, кто
  заводит сотрудника, и сообщает его лично)
