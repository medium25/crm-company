# Приём/выдача лидов — Apps Script Web App

Код в этой папке — не часть сборки Vite, он живёт отдельно, в **двух
разных** проектах Google Apps Script:

- `Code.gs` + `appsscript.json` — сам API (Web App), standalone-проект.
- `SheetsSync.gs` — синхронизация ИЗ Google-таблицы В CRM, живёт
  container-bound скриптом ВНУТРИ таблицы (Extensions → Apps Script из
  самой таблицы), не в standalone-проекте выше. Обращается к Web App как
  обычный внешний клиент — тот же apiKey, что и у любой другой интеграции.
  Может читать листы ИЗ ДРУГОЙ таблицы (не той, к которой привязан) через
  `SPREADSHEET_ID`, и несколько листов сразу через `SHEET_NAMES` — см.
  настройку ниже и комментарий в начале файла.
- `SheetsExport.gs` — обратная сторона: экспорт лидов ИЗ CRM В Google-
  таблицу, ОДИН лист, статус лида в отдельной колонке (in process/qual/
  won/lost, обновляется на месте при смене стадии в CRM). Тоже
  container-bound, тоже свой отдельный Apps Script проект (в ДРУГОЙ
  таблице, не в той, что льёт лидов внутрь) — см. комментарий в начале
  файла за настройкой и назначением колонок.

Файлы здесь хранятся как источник правды и для code review; заливать их в
script.google.com нужно вручную (или через `clasp push`, если он у тебя
настроен).

## Почему не Cloud Functions

Проект на бесплатном Firebase Spark-плане, Cloud Functions требуют платный
Blaze (см. `scripts/seed.js` и `docs/superpowers/specs/2026-08-13-leads-funnel-redesign.md`).
Вместо этого API живёт как Google Apps Script Web App (бесплатно, без
привязки карты) и пишет в тот же Firestore напрямую через его REST API,
используя сервис-аккаунт.

## Разовая настройка

### 1. Сервис-аккаунт с доступом к Firestore

В [Google Cloud Console](https://console.cloud.google.com/) → выбери проект
`crm-company-81ddd` (тот же `VITE_FB_PROJECT_ID`, что в `.env`):

1. IAM & Admin → Service Accounts → Create Service Account.
   Имя, например, `leads-api`.
2. Роль — **Cloud Datastore User** (`roles/datastore.user`) — минимально
   достаточно для чтения/записи Firestore, лишнего не даёт.
3. Keys → Add Key → Create new key → JSON. Скачается файл — в нём
   `client_email` и `private_key`, они понадобятся на шаге 3.

### 2. Новый проект Apps Script

1. [script.google.com](https://script.google.com) → New project.
2. Вставь содержимое `Code.gs` из этой папки в `Code.gs` проекта.
3. Project Settings (шестерёнка слева) → включи "Show appsscript.json
   manifest file in editor" → замени содержимое `appsscript.json` на файл
   из этой папки.

### 3. Script Properties

Project Settings → Script Properties → Add script property:

| Property                     | Значение                                             |
|-------------------------------|-------------------------------------------------------|
| `FIRESTORE_PROJECT_ID`        | `crm-company-81ddd`                                    |
| `SERVICE_ACCOUNT_EMAIL`       | `client_email` из скачанного JSON-ключа               |
| `SERVICE_ACCOUNT_PRIVATE_KEY` | `private_key` из JSON-ключа, целиком, вместе со строками `-----BEGIN PRIVATE KEY-----`/`-----END PRIVATE KEY-----` |
| `DEFAULT_BRANCH_ID`           | `icon-main` (можно не задавать — это значение по умолчанию) |

### 4. Деплой как Web App

Deploy → New deployment → тип **Web app**:
- Execute as: **Me** (владелец скрипта — так сервис-аккаунт используется
  через код, а не через личность вызывающего).
- Who has access: **Anyone**.

Скопируй выданный URL вида
`https://script.google.com/macros/s/AKfycb.../exec` — это и есть базовый
URL API, подставь его в `API.md` и в Apps Script (Google Sheets), который
будет слать туда лиды.

### 5. Ключ для интеграции

С машины, где настроен `.env` этого репозитория:

```
node --env-file=.env scripts/manage-api-keys.mjs create "Google Sheets" write
```

Выведенное значение `key` (`sk_live_...`) — вставь в Apps Script со стороны
Google Sheets как параметр `apiKey`. См. `API.md` за примерами запросов.

## Смена таблицы-источника / несколько листов (SheetsSync.gs)

Скрипт `SheetsSync.gs` привязан к своей таблице как контейнер (шаг 1 в
начале файла), но реально читает данные через `SPREADSHEET_ID` / `SHEET_NAMES`
в Script Properties — их можно менять без переноса кода в другую таблицу:

| Property         | Значение                                                          |
|-------------------|--------------------------------------------------------------------|
| `SPREADSHEET_ID`  | id ДРУГОЙ таблицы из её URL (`.../d/<это>/edit`) — читать не ту, к которой скрипт привязан. Не задан — читается таблица-контейнер. |
| `SHEET_NAMES`     | имена листов через запятую, например `Лиды` или `Meta 1, Meta 2, Meta 3`. Не задан — берётся старый `SHEET_NAME` (один лист), иначе активный лист. |

**Переключить на новую таблицу** (например, старая исчерпала себя, дальше
лиды льются в новую): открой script.google.com у `SheetsSync.gs` → Project
Settings → Script Properties → впиши `SPREADSHEET_ID` новой таблицы (и
`SHEET_NAMES`, если лист называется иначе, чем раньше). Убедись, что
аккаунт, под которым выполняется скрипт, имеет доступ к новой таблице
(минимум Viewer, `getDataRange` только читает, но `ensureTrackingColumns_`
дописывает служебные колонки — нужен Editor). Проверь `testSyncOneRow`
перед тем как ждать триггер — он покажет, какой именно лист сейчас
сконфигурирован. Триггер (`installTrigger`) переустанавливать не нужно —
он просто вызывает `syncNewLeadsToCrm`, а тот уже читает актуальные
Script Properties при каждом тике.

**Добавить ещё листы** (сейчас один, потом добавятся): просто дозаписать
имя через запятую в `SHEET_NAMES` — код уже поддерживает несколько листов
за один проход (общий бюджет `MAX_ROWS_PER_RUN` = 25 строк на ВСЕ листы
вместе за тик, не на каждый по 25). Условие — одинаковые заголовки колонок
на всех листах (один `COLUMN_MAP` в файле на все); если у нового листа
другая структура колонок — нужна отдельная доработка, не текущий код.

## Ежедневный отчёт по операторам → Telegram

Живёт в том же `Code.gs` (тот же standalone-проект, тот же сервис-аккаунт —
отдельный проект под это не нужен). Раз в 5 минут проверяет по каждому
активному оператору, не настал ли момент слать ЕМУ отчёт (10 минут до конца
ЕГО смены на сегодня, из `settings/{branchId}.operatorSchedules`), и если
да — считает 6 метрик за 24 часа перед этим моментом и шлёт сообщение в
топик «Отчёты» Telegram-группы. Оператора без активности за окно (все
метрики — 0) пропускает молча.

### 1. Бот и группа

1. В Telegram напиши [@BotFather](https://t.me/BotFather) → `/newbot`,
   следуй подсказкам — получишь токен вида `123456:AAH...`.
2. Добавь бота в нужную группу (группа должна быть с включёнными темами/
   топиками — «Group settings → Topics»).
3. Узнай `chat_id` группы и `message_thread_id` топика «Отчёты»:
   - Напиши любое сообщение в топик «Отчёты» от своего аккаунта.
   - Открой в браузере `https://api.telegram.org/bot<TOKEN>/getUpdates`
     (подставь свой токен) — в ответе JSON найди `chat.id` (отрицательное
     число для групп) и `message_thread_id` у своего сообщения.

### 2. Script Properties (добавь к таблице из шага 3 выше)

| Property                     | Значение                                    |
|-------------------------------|----------------------------------------------|
| `TELEGRAM_BOT_TOKEN`          | токен от BotFather                            |
| `TELEGRAM_CHAT_ID`            | `chat_id` группы (со знаком минус)            |
| `TELEGRAM_REPORTS_THREAD_ID`  | `message_thread_id` топика «Отчёты»           |

### 3. Установка триггера (один раз)

В редакторе script.google.com — выпадающий список функций сверху → выбери
`installDailyOperatorReportTrigger` → **Run**. Безопасно перезапускать
(сносит старый триггер с тем же именем перед созданием нового).

### 4. Проверка перед тем, как доверять графику

Выбери `previewDailyOperatorReports` → **Run** → открой Execution log
(Ctrl+Enter). Посчитает отчёт по каждому оператору за последние 24 часа
ПРЯМО СЕЙЧАС (без привязки к графику) и просто напечатает — ничего не
отправляет в Telegram. Проверь, что цифры похожи на правду, прежде чем
полагаться на реальный триггер.

### Если что-то не так

- **Отчёт не приходит** — проверь, что у оператора вообще задан график на
  сегодняшний день недели в Настройки → Распределение лидов, и что он был
  активен за окно (иначе отчёт по нему намеренно не шлётся).
- **Приходит не в тот топик / не в ту группу** — перепроверь `chat_id`/
  `message_thread_id` через `getUpdates`, как в шаге 1.
- Логи каждого тика триггера — Executions (иконка часов слева в редакторе).

## Редактирование текста отчёта прямо из Telegram

Текст отчёта — шаблон с плейсхолдерами (`{{name}}`, `{{periodStart}}`,
`{{periodEnd}}`, `{{leads}}`, `{{taken}}`, `{{lost}}`, `{{target}}`,
`{{other}}`, `{{payments}}`), хранится в Script Property `REPORT_TEMPLATE`.
Меняется командами боту в Telegram — без правки кода. По умолчанию —
редактировать может кто угодно, кто напишет боту (осознанно открыто).
Ограничить одним человеком — задать `ADMIN_TELEGRAM_USER_ID`, тогда команды
сработают только от него.

Работает через опрос (та же схема, что у `SheetsSync.gs`), не webhook —
Apps Script Web App всегда отвечает на первый запрос 302-редиректом
(`script.google.com` → `script.googleusercontent.com`), а Telegram при
доставке через webhook эту цепочку не проходит и репортит «Wrong response
from the webhook: 302 Found», `doPost` с апдейтом при этом не выполняется
вообще. Опрос эту проблему обходит — Apps Script сам инициирует запрос к
Telegram по таймеру, а не наоборот.

### Разовая настройка

1. Выбери `installTelegramCommandPolling` в списке функций → **Run** —
   один раз. Снимет случайно оставшийся webhook (несовместим с опросом) и
   поставит триггер раз в 10 минут. Безопасно перезапускать.
2. Напиши боту `/start` (в личку или в ту же группу) — в течение 10 минут
   должен ответить меню с шаблоном и кнопками.
3. (Опционально, чтобы закрыть только собой) Узнай свой Telegram `user_id` —
   `getUpdates`, поле `message.from.id` у твоего сообщения → добавь
   `ADMIN_TELEGRAM_USER_ID` в Script Properties.

### Меню (админ, либо кто угодно — см. выше)

`/start` (или `/menu`, `/gettemplate`) — присылает текущий шаблон и три
inline-кнопки: «👁 Показать шаблон», «✏️ Изменить шаблон», «♻️ Сбросить на
стандартный». «Изменить» просит прислать новый текст следующим сообщением
(эмодзи, порядок строк, формулировки — что угодно, плейсхолдеры сохрани
нужные) — ждёт 10 минут, после сохраняет и присылает меню снова.

Те же действия — текстовыми командами, если удобнее: `/gettemplate`,
`/settemplate` и с новой строки текст, `/resettemplate`.

### Если команды не отвечают

- Проверь `ADMIN_TELEGRAM_USER_ID` — сверка строгая по `from.id`.
- `installTelegramWebhook` нужно перезапустить после смены URL деплоя
  (Deploy → Manage deployments → новая версия меняет `/exec` URL только
  если создан НОВЫЙ deployment, не при New version — но проверить лишним
  не будет).
- Логи webhook-запросов — тоже в Executions, ищи `doPost`.

## Ограничения этой платформы (важно прочитать)

- **HTTP-статус всегда 200.** Apps Script Web App не даёт вернуть настоящий
  400/401/429 на транспортном уровне — единственный способ узнать исход
  запроса это поле `status` внутри JSON-тела ответа.
- **Заголовок `Authorization` недоступен.** Apps Script не прокидывает
  произвольные заголовки в `doGet(e)`/`doPost(e)`. Ключ передаётся полем
  `apiKey` в теле (POST) или query-параметром `?apiKey=` (GET).
- **PATCH не поддерживается как метод** — Web App принимает только GET/POST.
  Обновление лида — это `POST` с `{"action": "update", ...}`.
- Я не могу выполнить/протестировать этот код напрямую (нет среды
  выполнения Apps Script у меня под рукой) — после деплоя прогони
  `scripts/test-leads-api.mjs` (см. корень репозитория) и проверь глазами.

## Предпосчитанные цифры дашборда (DashboardStats.gs)

Файл живёт в ТОМ ЖЕ проекте Apps Script, что `Code.gs` (общие Script Properties,
общий сервис-аккаунт) — вставь его туда же как отдельный файл, ничего
дополнительно настраивать не нужно.

1. Вставь `DashboardStats.gs` в проект (тот же, где `Code.gs`).
2. Выбери функцию `refreshDashboardStats` в выпадающем списке вверху редактора → Run —
   заполнит `dashboardStats/{branchId}` сразу, иначе дашборд будет висеть на
   «Цифры дашборда ещё не посчитаны» до первого срабатывания триггера.
3. Выбери `installDashboardStatsTrigger` → Run — ставит почасовой триггер (реально
   считает только 7:00–23:00 по Ташкенту, вне этих часов выходит без единого чтения).

После этого дашборд в CRM подписан на один маленький документ вместо того, чтобы
каждый сотрудник на каждом заходе пересчитывал всё сам.

## Квоты и частота триггеров (экономия)

Суточные лимиты, которые легко выбрать: `UrlFetchApp` (20 000 вызовов) и чтения Firestore
(50 000 на Spark). Что и как часто запускается:

| Проект / функция | Частота | Заметки |
|---|---|---|
| SheetsSync `syncNewLeadsToCrm` | каждую минуту | 10 строк за тик; при исчерпанной квоте сам встаёт на паузу до сброса; упавшая строка — `ERR#n` с паузой 5/15/60/180 мин, на 5-й `СТОП#`. Сброс вручную — `retryFailedRows` |
| SheetsExport `exportOnce` | раз в сутки (`installExportTrigger` — раз в 8 часов) | won за 2 месяца, lost за текущий, остальное не читается; смена статуса идёт через webhook `doPost` |
| Code.gs `checkTelegramCommands_` | каждые 10 минут | раньше каждую минуту — 1440 вызовов в сутки |
| Code.gs `checkAndSendDailyOperatorReports` | каждые 5 минут | график смен и операторы — из кэша на 30 минут |
| DashboardStats.gs `refreshDashboardStats` | раз в час, реально считает только 7:00–23:00 по Ташкенту | 6 плиток + график дашборда одним запуском на весь филиал → `dashboardStats/{branchId}`; раньше это считал КАЖДЫЙ сотрудник на каждом заходе на дашборд (100 618 из 148 026 чтений за 21.09.2026) |

Кэш в Code.gs (`CacheService`): API-ключ 2 мин (отзыв ключа действует не позже чем через 2 минуты),
настройки филиала и список операторов 5 мин, имена операторов 10 мин, `lastUsedAt` ключа пишется не чаще раза в 10 минут.
Загрузка оператора считается запросом COUNT (~1 чтение), при отказе агрегатов — прежним чтением до 500 документов.
`list` отдаёт до 1000 лидов за страницу (`per_page=1000`), чтобы не перечитывать стадию на каждой странице.

Нельзя держать второй проект с тем же `syncNewLeadsToCrm` по тому же листу — он удваивает расход.

## Учёт квот (раздел «Настройки → Лимиты и расход» в CRM)

Каждый скрипт сам считает свои запросы UrlFetch и время работы (`trackedRun_`, `fetch_`) и раз в 10 минут отправляет
счётчики: `Code.gs` пишет их прямо в Firestore (`settings/appsusage_{сутки квоты}`), `SheetsSync.gs` и `SheetsExport.gs`
присылают их в `Code.gs` действием `usage` (нужен обычный API-ключ). Код тоже считает чтения/записи Firestore, которые
делает сам `Code.gs`. Отправка стоит один запрос UrlFetch на 10 минут; при ошибке счётчики остаются в очереди.
Ключи функций: `trg_*` — триггеры (идут в квоту «время триггеров» 90 мин), `web_*` — веб-приложение.
После обновления файлов ничего запускать не нужно — данные появятся на вкладке в течение 10 минут.
